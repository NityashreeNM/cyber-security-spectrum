# 1.1.3 — Cybersecurity Principles

## 1. Overview

Cybersecurity principles are foundational guidelines used to make security decisions across the system lifecycle.

They help organizations:

- Design secure systems
- Limit access and exposure
- Reduce the impact of failures or compromise
- Detect and respond to harmful activity
- Maintain essential services
- Support consistent risk-based decisions

Principles do not replace controls or requirements. They guide how security controls are selected, combined, and evaluated.

## 2. Principle, Policy, Requirement, and Control

These terms describe different levels of security guidance:

| Term | Meaning | Example |
|---|---|---|
| Principle | A general rule that guides decisions | Apply least privilege |
| Policy | An organization-approved rule or management directive | Privileged access requires approval |
| Requirement | A specific condition a system or process must meet | Administrator accounts must use multi-factor authentication |
| Control | A measure used to meet a requirement | A technical access-control policy and MFA enforcement |
| Evidence | Information showing whether a control operates as intended | Authentication logs and configuration records |

Principles support consistent decision-making, while requirements and controls establish what must be implemented.

## 3. Least Privilege

Least privilege means giving users, applications, services, and systems only the access and permissions required to perform authorized functions.

Implementation may include:

- Role-based access
- Temporary administrative access
- Separation of normal and privileged accounts
- Time-limited permissions
- Service accounts with restricted capabilities
- Regular access reviews
- Removal of unused permissions

**Example:** A reporting application should receive read-only access to a report database rather than administrator permissions.

Least privilege reduces:

- Accidental misuse
- The impact of compromised accounts
- Unauthorized access to sensitive functions
- Damage caused by software or configuration errors
- Opportunities for privilege escalation

## 4. Defense in Depth

Defense in depth uses multiple independent or complementary layers of protection.

A security failure at one layer should not allow an attacker to reach a desired target without overcoming additional controls.

Defense in depth may combine:

- Identity and access controls
- Multi-factor authentication
- Secure configuration
- Network segmentation
- Endpoint protection
- Application security
- Encryption
- Monitoring and logging
- Incident response
- Backups and recovery

**Example:** Even if an account is compromised, segmentation, least privilege, endpoint monitoring, and application controls can reduce the attacker’s ability to access or modify important systems.

Defense in depth should use useful diversity and not merely add duplicate controls. Each layer should address a realistic risk and contribute a measurable benefit.

## 5. Separation of Duties

Separation of duties divides critical responsibilities between different people or roles so that no individual can complete a sensitive process without appropriate oversight.

Examples include:

- Different people request, approve, and implement system changes
- Financial transactions require more than one authorization
- Developers do not directly approve or deploy production changes without established controls
- The person managing access is not solely responsible for approving every access request
- Security logs are protected from users who can modify the monitored systems

Separation of duties helps prevent fraud, unauthorized changes, and accidental or malicious abuse.

Where staffing makes strict separation difficult, organizations can use compensating controls such as:

- Restricted permissions
- Detailed logging
- Independent reviews
- Dual approval
- Time-limited administrative access
- Supervision or monitoring

## 6. Need-to-Know and Data Minimization

People and systems should receive information only when it is required for a legitimate function.

Related measures include:

- Data classification
- Restricted record access
- Data minimization
- Purpose limitation
- Controlled data sharing
- Secure data retention and disposal
- Protection of highly sensitive and personally identifiable information

**Example:** A support technician should receive the minimum user information required to resolve a ticket, rather than unrestricted access to every customer record.

Need-to-know and data minimization reduce privacy risk and limit the impact of unauthorized disclosure or account compromise.

## 7. Secure by Design

Secure by design means considering security requirements from the beginning rather than adding protection after implementation.

It includes:

- Identifying assets and security objectives
- Defining trust boundaries
- Performing threat modelling
- Designing strong authentication and authorization
- Applying secure configuration defaults
- Protecting data flows
- Validating inputs
- Limiting dependencies
- Planning logging and monitoring
- Designing for recovery
- Testing controls before deployment

Security should be built into architecture, software development, procurement, configuration, and operational procedures.

## 8. Secure by Default

Secure by default means systems should use secure settings before additional customization.

Examples include:

- Requiring authentication
- Disabling unnecessary services
- Using encrypted communication
- Restricting administrative interfaces
- Enabling appropriate logging
- Applying standard security baselines
- Avoiding known or predictable default credentials
- Providing safer error handling
- Applying least privilege to default accounts and roles

Users should not need to locate and enable complex security features simply to achieve an acceptable baseline.

## 9. Fail Secure and Fail Safe

These concepts address how a system behaves when a component fails.

### Fail secure

A fail-secure system reduces unauthorized access or unsafe digital behavior when failure occurs.

**Example:** When a security-control device loses communication, it stops unauthorized access to a protected area rather than allowing unrestricted entry.

### Fail safe

A fail-safe system prioritizes protecting people, property, or the environment when a failure occurs.

**Example:** A safety control stops an industrial process into a defined safe state rather than allowing an unsafe process to continue.

Fail secure and fail safe are not always identical. Security decisions in cyber-physical environments must account for both cybersecurity and safety.

## 10. Zero Trust

Zero Trust is a security strategy based on the principle that trust should not be granted solely because a system, device, or user is inside a traditional network boundary.

Zero Trust concepts include:

- Explicitly verify identities and devices
- Apply least privilege
- Assume that threats may exist inside or outside the network
- Limit lateral movement
- Evaluate every access request using relevant context
- Authenticate and authorize before access
- Use continuous monitoring and risk evaluation
- Protect each resource based on its sensitivity and exposure
- Limit the lifetime and scope of privileges

Zero Trust is not a single product or complete removal of trust. It is an architecture and operating model that continuously evaluates access and risk.

## 11. Trust Boundaries

A trust boundary identifies where the level of trust or security context changes.

Examples include:

- A user device connecting to an application
- An application communicating with a database
- One network zone communicating with another
- A cloud service connecting to an on-premises system
- A third-party application exchanging data
- A human operator changing an industrial control configuration

Security controls at trust boundaries may include:

- Authentication
- Authorization
- Encryption
- Input validation
- Network filtering
- Data-loss prevention
- Logging
- Mutual verification between components

Identifying trust boundaries helps analysts determine where authentication, validation, monitoring, and segmentation are required.

## 12. Defense Through Visibility and Accountability

Systems should provide sufficient visibility to detect misuse and attribute actions to responsible entities.

Useful capabilities include:

- Individual accounts
- Protected and centralized logs
- Time synchronization
- Alerting and monitoring
- Audit trails
- Configuration baselines
- Security-event correlation
- Change records
- Independent log protection
- Defined responsibilities

Visibility supports incident detection and investigation. Accountability requires both reliable records and clear organizational ownership.

## 13. Avoiding a Single Point of Failure

Security and availability should not depend on a single uncontrolled component when significant consequences could result.

Potential measures include:

- Redundant services
- Independent failure domains
- Secure backups
- Failover arrangements
- Recovery procedures
- Alternate communication methods
- Spare or replaceable components
- Cross-training operational personnel
- Tested recovery plans

The purpose is not simply to add more components. Redundant components must be independent enough to survive common threats and failures.

## 14. Resilience and Recovery as Design Principles

System and organizational design should account for compromise or disruption.

This includes:

- Predefined recovery objectives
- Verified backups
- Isolated recovery environments
- Tested restoration procedures
- Alternative operating methods
- Incident-response planning
- Supply-chain alternatives
- Preservation of trusted configuration records
- Lessons learned and continuous improvement

Prevention reduces the likelihood of disruption. Detection limits the time that harmful activity continues. Response and recovery limit the impact and restore normal operations.

## 15. Security Control Categories

A useful security model combines different types of controls.

| Control category | Purpose | Examples |
|---|---|---|
| Preventive | Stop unwanted events | Access control, secure configuration, encryption |
| Detective | Identify or investigate unwanted events | Logging, monitoring, security alerts |
| Corrective | Reduce harm or restore a desired state | Patching, account reset, rollback |
| Recovery | Restore services after disruption | Backups, restoration, disaster recovery |
| Deterrent | Influence behavior or discourage abuse | Security warnings, acceptable-use policies |
| Compensating | Provide an alternative safeguard | Extra review, enhanced monitoring, manual approval |

Controls may belong to several categories. Each control should support a defined objective and be monitored for effectiveness.

## 16. Security Principles in Practice

Security decisions should be evaluated using the organization’s mission, threats, operational constraints, and acceptable risk.

**Example: Protecting a payroll application**

- Apply least privilege to payroll roles.
- Separate request, approval, and change functions.
- Use multi-factor authentication for privileged access.
- Restrict and monitor administrative activity.
- Encrypt sensitive data.
- Apply network segmentation.
- Log user and administrator actions.
- Protect audit records.
- Back up records and test restoration.
- Prepare for incident response and recovery.

No principle should be applied mechanically. The goal is to select appropriate safeguards while maintaining legal, operational, privacy, safety, and usability requirements.

## 17. Common Misconceptions

### Misconception 1: Defense in depth means installing as many tools as possible

**Correction:** Effective defense in depth uses complementary, proportionate controls that address realistic threats and weaknesses.

### Misconception 2: Least privilege means removing all permissions

**Correction:** Least privilege gives each entity only the permissions required for legitimate functions.

### Misconception 3: Separation of duties always requires a large team

**Correction:** Compensating controls such as logging, review, dual approval, and automated controls may reduce the need for larger staffing, although they do not remove accountability.

### Misconception 4: Zero Trust means no one can ever be trusted

**Correction:** Zero Trust reduces implicit trust and makes access decisions based on verified identity, device state, resource sensitivity, and other relevant context.

### Misconception 5: A security principle guarantees security

**Correction:** Principles guide decisions but must be implemented, configured, monitored, and assessed against real risks.

## 18. Key Takeaways

1. Cybersecurity principles are general guidelines for consistent, risk-based security decisions.
2. Least privilege limits permissions and reduces the effect of misuse or compromise.
3. Defense in depth uses complementary layers rather than relying on a single safeguard.
4. Separation of duties limits misuse and improves authorization and oversight.
5. Secure-by-design and secure-by-default approaches address security earlier in the lifecycle.
6. Trust boundaries identify where identity, access, and data protection must be enforced.
7. Zero Trust reduces implicit trust and validates access decisions using relevant context.
8. Security controls should prevent, detect, correct, and recover from adverse events.
9. Principles must be applied in proportion to risk and operational context.
